# Delayed observations and forecasts on 3 November 2026

The Cloudflare watchdog ran throughout the night and successfully launched
refreshes. At 13:07 UTC its history contained 76 checks and 12 recovery
dispatches. The latest successful publication was at 11:17 UTC; the forecast
still came from 08:45 UTC.

## Causes

1. Collection successfully fetched Energinet power data, then forecasting made
   a separate request to the same dataset seconds later. The latter returned
   HTTP 429. The failed 12:26 UTC run collected power at 12:44:59, then reported
   the forecast request failure at 12:45:01. Retries correctly stopped when the
   provider's requested delay exceeded the forecasting job's wait budget.
2. The watchdog uses `workflow_dispatch`. Existing deployment-validation gates
   treated every non-scheduled run as a code deployment, so the forecast failure
   prevented publishing successfully collected observations. The new watchdog
   integration did not account for this distinction. The regular scheduled run
   at 10:44 UTC did publish observations while retaining the older forecast.

The request duplication predated the watchdog. Its new dispatch path exposed
the publication-policy gap. These logs establish the HTTP 429 responses, but
do not establish whether Energinet changed its limits or whether shared runner
traffic contributed that morning.

Evidence: [failed recovery run](https://github.com/HuayuanSong/open-current/actions/runs/41635782919),
[successful scheduled publication](https://github.com/HuayuanSong/open-current/actions/runs/41621756519),
[watchdog history](https://open-current-watchdog.naermad.workers.dev/history).
Energinet's [API guidance](https://www.energidataservice.dk/guides/api-guides)
describes dataset-specific limits and recommends matching request frequency to
the dataset's update frequency.

## Corrections and validation

- Share the complete three-day power response between collection and forecasting.
  Retain the original collection time. Reject old, future, incomplete or
  insufficient-window cache entries; initial 35-day bootstrap still fetches its
  required history. Hourly normalization, missingness rules and models are unchanged.
- Treat `workflow_dispatch` with `refresh: true` as an operational refresh for
  forecast/trial publication gates. Code pushes and validation-only dispatches
  remain strict. Model parity checks, data tests and browser checks remain enabled.
- Regression tests compare shared-response results with direct-fetch results,
  assert no duplicate request, check cache rejection, and preserve the last
  complete response when collection is truncated. The full local Python suite
  passes (70 tests). The workflow condition matrix was checked for push,
  schedule and both dispatch input values.
- A live collection at 13:16 UTC returned 2,070 power records. Forecast input
  preparation reused it with zero additional source requests and recovered
  complete observations through 13:00 UTC.

The watchdog still starts recovery only after an hour without publication.
Its polling interval and collection time mean this is a backup, not a guarantee
of half-hour publication. The original 48-hour observation window remains in
progress; successful deployment alone does not establish continued reliability.
